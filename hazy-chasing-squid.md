# End-to-End AI Workflow - Focused Implementation Plan

> **Precursor Plan**: [agile-wibbling-dawn.md](./agile-wibbling-dawn.md) - n8n-based workflow architecture addressing OpenCode system prompt issues.

## Summary

**Approach**: Azure DevOps as central hub. Reference-based data flow with PR approval gates.

**Key Principles**:
1. **Reference-based**: Pass file paths/commit SHAs between phases (not file contents)
2. **Approval gates**: Every artifact creates a PR requiring approval before next phase
3. **New workflow**: Create new n8n workflow - existing workflows unchanged
4. **Importable outputs**: Each artifact in standard format for its target system

**Repositories**:
- `{org}-docs` - Single repo for all projects with shared architecture + project folders
- `{project}-code` - Source code per project (generated by dev phase)
- Azure DevOps - Work items (Features, Stories, Tasks) per project
- ADOIT - Enterprise architecture models (imported from shared ArchiMate files)

**Multi-Project Structure**:
```
{org}-docs/
├── architecture/                    # SHARED - stable enterprise architecture
│   ├── business.archimate          # Used for impact analysis across projects
│   ├── data.archimate
│   ├── application.archimate
│   ├── technology.archimate
│   └── adoit-import.xlsx
│
└── projects/
    ├── {project-a}/
    │   ├── docs/
    │   │   ├── BRD.md              # Project-specific
    │   │   └── PRD.md
    │   ├── api/
    │   │   └── openapi.yaml        # Project-specific solution architecture
    │   ├── db/
    │   │   └── schema.sql
    │   └── backlog/
    │       ├── ado-stories.json
    │       └── estimates.json
    │
    └── {project-b}/
        ├── docs/
        ├── api/
        ├── db/
        └── backlog/
```

**Key Principles**:
- **Shared architecture** = Stable, versioned via Git, used for impact analysis
- **Project artifacts** = Isolated per project folder
- **Impact analysis** = Reference shared architecture to assess changes

### Reference Format Between Phases
```json
{
  "phaseInput": {
    "repo": "{org}-docs",
    "project": "project-a",
    "branch": "feature/{project}/phase-{n}",
    "commitSha": "abc123...",
    "files": {
      "shared": [
        "architecture/application.archimate"
      ],
      "project": [
        "projects/project-a/docs/BRD.md"
      ]
    },
    "loadStrategy": {
      "architecture/application.archimate": "selective",
      "projects/project-a/docs/BRD.md": "summary"
    },
    "prUrl": "https://dev.azure.com/{org}/{project}/_git/{repo}/pullrequest/123",
    "approvedAt": "2024-01-15T10:00:00Z"
  }
}
```

**Load Strategies**:
- `full` - Load entire file (default, use sparingly)
- `summary` - Load auto-generated summary section only (~500 tokens)
- `selective` - Load filtered sections based on domain/elements

## Large Output / Context Limit Mitigation

### The Problem
- LLM context windows are limited (e.g., 128K-200K tokens)
- Large architecture files, OpenAPI specs, or PRDs can exceed limits
- Passing full file contents between phases compounds the problem

### Mitigation Strategies

| Strategy | When to Use | Implementation |
|----------|-------------|----------------|
| **1. Reference-only passing** | Between all phases | Pass file paths + commit SHAs, not content. Agents fetch only needed sections. |
| **2. Selective loading** | Architecture → Solution Design | Load only relevant ArchiMate layers (e.g., Application layer for API design) |
| **3. Chunked generation** | Large OpenAPI/SQL output | Generate in sections: endpoints by domain, then schemas, then combine |
| **4. Summarization** | BRD/PRD for story generation | Create executive summary (~500 tokens) for context, full doc available via ref |
| **5. Streaming output** | All agent phases | Use streaming JSON output to detect token limit before failure |
| **6. Domain filtering** | Impact analysis | Filter architecture to affected domains only |

### Implementation Details

#### 1. Reference-Only Passing (Primary Strategy)
```json
{
  "phaseInput": {
    "repo": "{org}-docs",
    "project": "project-a",
    "commitSha": "abc123",
    "refs": [
      {"path": "projects/project-a/docs/BRD.md", "loadStrategy": "summary"},
      {"path": "architecture/application.archimate", "loadStrategy": "selective", "filter": "components"}
    ]
  }
}
```

#### 2. Selective Architecture Loading
For impact analysis, only load relevant sections:
```python
# Instead of loading entire architecture
architecture_context = load_archimate_selective(
    file="architecture/application.archimate",
    filter={
        "elements": ["ApplicationComponent", "ApplicationService"],
        "relationships": ["Serving", "Realization"],
        "names_containing": ["Patient", "Auth"]  # Domain filter
    }
)
```

#### 3. Chunked OpenAPI Generation
```yaml
# Phase 3.5 generates in chunks:
# Chunk 1: Core resource endpoints (patients, appointments)
# Chunk 2: Supporting endpoints (auth, notifications)
# Chunk 3: Schemas and components
# Final: Merge and validate
```

#### 4. Document Summarization
Each BRD/PRD includes auto-generated summary for downstream phases:
```markdown
<!-- AUTO-GENERATED SUMMARY (for agent context) -->
## Executive Summary
- **Problem**: [1-2 sentences]
- **Key Features**: [bullet list, 5 max]
- **Critical Constraints**: [bullet list, 3 max]
- **Token Count**: 487
<!-- END SUMMARY -->

[Full document follows...]
```

### Token Budget Guidelines

| Artifact | Max Tokens | Strategy if Exceeded |
|----------|------------|---------------------|
| BRD.md | 4,000 | Use summary for downstream, full via ref |
| Architecture (per layer) | 8,000 | Selective loading by domain |
| OpenAPI.yaml | 10,000 | Chunk by domain, generate incrementally |
| PRD.md | 6,000 | Use summary for story generation |
| Schema.sql | 5,000 | Chunk by entity group |

### Monitoring & Alerts
- Track token usage per agent invocation
- Alert if output exceeds 80% of budget
- Log truncation events for debugging

### Repo Sync Strategy for OpenCode Agents

Each OpenCode agent must:
1. **Before execution**: `git pull origin main` (or feature branch)
2. **After execution**: `git add . && git commit -m "Agent: {name} output" && git push`

This is handled by a wrapper script or agent preamble:
```bash
# Agent preamble (in each agent .md or wrapper)
cd /workspace/{org}-docs
git checkout feature/{project}/phase-{n}
git pull origin feature/{project}/phase-{n}

# ... agent work ...

git add projects/{project}/
git commit -m "chore({project}): {agent-name} output"
git push origin feature/{project}/phase-{n}
```
