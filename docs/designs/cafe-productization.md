## Problem (validated by landscape)
Orgs want governed AI adoption but get slide decks, not running systems. 2026 data: 88% adopted AI somewhere, only **21% trust their governance**, **79% struggle**, 54% of C-suite say AI adoption is "tearing the company apart." Competitors sell either a *platform* (watsonx, Azure Foundry) or a *consultancy*, and governance as an after-the-fact *gate*. Gap: nobody productizes the *method* that turns a use case into a governed, running architecture across sovereign AND cloud tiers, for AI AND traditional work.

## Vision

### 10x Check
The ideal (C) is not a demo of a platform. It's a Chief Architect dropping in *their* use case — even messy (a doc, a Jira epic, a sentence) — and watching it become, in the room: (1) a governed CAFE-mapped architecture, (2) **provisioned running infra** on their chosen tier (local or their Azure), (3) with governance gates visible — identity, eval, DLP, ontology — as it's built. Felt experience: *"we compressed our 6-month adoption program into a Tuesday afternoon, and it's governed by default."*

### Platonic Ideal
CAFE as the **"Terraform of AI adoption"**: declare the outcome → agents *plan* it (CAFE architecture) → the IDP *applies* it (running platform) → governance is the type system. Substitutable across sovereign/cloud — which structurally kills the market's #1 fear (lock-in).

### Differentiator (the wedge)
**Governance-as-generator, not governance-as-veto.** Competitors audit someone else's system after the fact. CAFE *produces* the governed system. Made visible by the live governance scorecard.

## Positioning
- **Horizontal** ("any organisation"), proven through a **simple, universally-relatable operational use case**: **Accounts-Payable invoice exception handling** — a deterministic traditional backbone (intake → OCR → 3-way match → ERP → approval-queue UI) plus a genuinely agentic exception layer (investigate → decide → draft vendor email). Splits cleanly into **"deterministic detect / agentic decide,"** showcasing OAM auto-provisioning the traditional half and Foundry/Copilot/Claude-Code composing the AI half. Alternatives (same shape): order/fulfillment exception management, IT incident triage.
- Two commercial offers pitched off the same demo (named to avoid colliding with the build-stage letters A/B/C below):
  - **Product Offer** = the product that embodies CAFE (the SaaS control plane = build stages B→C).
  - **Framework Offer** = CAFE framework adoption / consultancy / IP licensing.

> **Terminology:** "A / B / C" always mean **build stages** in this doc. The commercial offers are always written out as **Product Offer** / **Framework Offer** — never as bare letters.

## Roadmap (A → B → C) — staged build, highest-ready-tier demoed live, lower tiers as fallback

```
 STAGE A (vehicle, floor)      STAGE B (product)              STAGE C (ideal, live)
 curated walkthrough      -->  CAFE control plane        -->  live "your use case" at the
 AP-invoice-exception          intake -> tier selector        presentation: drop in a use
 use case, both tiers           -> pipelines -> OAM -> IDP     case, watch governed arch
 -> IDP-provisioned result      -> live platform link +        compose + provision live,
 (pre-built artifacts)          live GOVERNANCE SCORECARD      dual-tier, AI+traditional
 ALWAYS WORKS (fallback)        semi-live capable              highest wow, highest risk
```

**Demo-day rule:** present the highest tier that is *reliably* ready; lower tiers are graceful fallbacks via a **demo control-room / fallback harness**. A is the floor that always works.

### Stage A deliverable set (the always-works floor — enumerate so it's buildable)
1. The AP-invoice-exception use-case input (one page: the brief the architecture is generated from).
2. Local-tier artifact set (n8n pipeline outputs: ontology, BRD/PRD, ArchiMate/C4, OAM).
3. Enterprise-tier artifact set (copilots Foundry/Power Platform outputs for the same use case).
4. A short screen-recording of the IDP applying the OAM → running platform (the proof it implements).
5. A narrated click-through (slides or a board) stitching 1→4 with the two takeaways called out.
6. Two one-pagers: **Product Offer** and **Framework Offer**, shown at the close.

### Stage gates
- **A done when:** deliverables 1–6 above exist and a Chief Architect, walked through them, says "you compressed our cycle into something I can buy."
- **B done when:** intake → tier selector → existing pipelines → OAM → IDP returns a working-platform link, with the live governance scorecard reflecting REAL checks. **Required real checks for B-done:** Presidio DLP + capability-registry coverage + CAFE 7-domain coverage. **Eval-gate is optional for B-done** ("wired in B+") and only shown as real once `copilots/evals` coverage is confirmed (Open Questions) — until then the scorecard must not display an eval score it can't back.
  - **Semi-live defined:** intake + architecture generation + governance scorecard run **live**; the IDP `apply` may return a **pre-provisioned** platform link (real infra, provisioned ahead of time) rather than provisioning during the demo.
- **C done when:** a use case **supplied live from a curated category** composes + provisions within demo tolerance, fallback one keypress away.
  - **Curated categories + accepted input shapes:** AP-invoice-exception, order/fulfillment-exception, IT-incident-triage (all "deterministic detect / agentic decide" shaped). Accepted input per category = a short structured brief (a paragraph or a filled template), NOT arbitrary free-text. (The "a doc / a Jira epic / a sentence" framing in the 10x Vision is the *aspirational* ideal, not the C-done bound.)
  - **Demo tolerance defined:** architecture compose + scorecard render in **< 90s**. **Dual-tier pass condition:** C passes when the **local** tier provisions live (KubeVela apply **< 2 min**) **AND** the **pre-warmed Azure** tier is revealed (real infra, provisioned ahead) — both shown within the window. If either exceeds tolerance, the control-room drops to the Stage-B pre-provisioned link automatically.

### `copilots/` prerequisite
`copilots/` is **not yet a git repo**. Initialize + version it **before** it backs the B build (the scorecard reads from `copilots/evals` and the capability registry). This is a **B prerequisite**, not parallel — do it during Stage A.

## Risks / inversion (what makes us fail)
- **Live demo stumble** at C → mitigated by the fallback harness + A as floor.
- **Governance theater** — a scorecard that shows green without real checks is worse than none. Every score it displays must be backed by a real check (Presidio DLP + capability registry + CAFE domains for B-done; eval-gate only once `copilots/evals` coverage is confirmed). Never display a score you can't back; never a script. **Non-negotiable: governance is always real, even when infra is staged (see next).**
- **Infra staging vs. theater (resolved):** at C the enterprise (Azure) `apply` may be **pre-warmed** — i.e. *real* infra provisioned ahead of time and revealed live — because Azure Bicep provisioning runs minutes-to-tens-of-minutes. This is NOT "fake-the-apply": the platform is genuinely running, just provisioned earlier. **Never** fake a green result. Local (KubeVela) apply is fast enough to run truly live. So: governance = always live+real; infra = live for local, pre-warmed-real for Azure.
- **Horizontal-but-thin** — without a vertical anchor, the AP-invoice-exception demo must be polished enough to feel real to any industry (AP is universal, which helps).
